# 客户价值、竞品差异与销售口径

本文件帮助销售、售前和实施围绕可验证价值沟通。任何效果描述都必须附带客户现状、数据质量、实施范围、第三方依赖和验收方法；不得使用无法证明的“保证增长”“零故障”“无限扩展”等绝对承诺。

## 一、客户买点

以下六项与程序中的 `FACTORY_PLATFORM_SALES_VALUE_PROPOSITIONS` 一一对应。指标名称只是取证方向，不是已经实现的效果；每次销售使用前必须补充客户基线、目标范围、数据源、周期、责任方和验收样本。

1. **一条从增长到现金的链路**
   - 客户问题：建站、广告、CRM、ERP各自报喜，却无法说明客户为何成交、订单是否赚钱。
   - 平台价值：以同一客户、产品、确认订单和财务标识贯通获客到现金。
   - 取证方向：收入来源追溯率、订单毛利对账、现金转换周期。
2. **同一内核支持国内、海外、B2B、B2C**
   - 客户问题：四套系统重复商品、库存、客户和财务事实。
   - 平台价值：共享核心对象，叠加国家、渠道和业务模式配置。
   - 取证方向：共用主数据比例、新市场上线周期、跨渠道库存一致率。
3. **只销售可以制造和交付的承诺**
   - 客户问题：营销、报价、产能和质量脱节，容易错单或延期。
   - 平台价值：08形成报价与订单意向，09结合产品、产能、质量和库存确认订单，12处理财务实际成本和现金。
   - 取证方向：报价周期、订单变更率、准时足量交付率。
4. **从一次成交延伸到长期客户价值**
   - 客户问题：成交后的服务问题、使用情况和复购机会散落在个人沟通中。
   - 平台价值：06持续汇聚画像和同意，10管理CRM、服务、续约和增购，11计算留存及LTV。
   - 取证方向：复购率、净收入留存率、客户终身价值。
5. **受治理、可执行的业务AI**
   - 客户问题：通用AI不了解企业事实，输出不可审计，也不能安全进入业务流程。
   - 平台价值：AI只消费获准事实，展示引用和限制，并将建议转为有人负责、可否决的任务。
   - 取证方向：事实引用率、人工复核记录、建议闭环率。
6. **渐进实施而非强制推倒重建**
   - 客户问题：企业既担心一次性替换风险，也担心新增工具继续形成孤岛。
   - 平台价值：按阶段建设原生能力，或通过适配器连接既有ERP、MES、财务和CRM。
   - 取证方向：连接器覆盖率、阶段上线时长、重复录入下降率。

## 三、销售发现问题

至少确认以下三组事实后再推荐方案：

1. **组织与渠道**
   - 有多少总部、区域、代理、品牌和客户实例？
   - 哪些配置需要统一，哪些必须由代理或客户自主维护？
   - 当前发布、升级和故障回退由谁负责？
2. **业务与数据**
   - 报价、合同、订单、库存、客户和财务分别以哪个系统为准？
   - 国内/海外、B2B/B2C 是否存在不同审批、价格、税费和履约流程？
   - 数据质量、历史迁移量、实时性和对账要求是什么？
3. **成功与风险**
   - 客户希望改善的指标是什么，当前基线和取数方式是否存在？
   - 哪些第三方授权、合规评估或内部审批会影响上线？
   - 试点结束时，哪些可观察结果决定继续、调整或停止？

## 四、按销售过程的话术

### 1. 开场定位

- “我们重点解决总部能力如何被代理和客户安全复用，同时保留各自数据与自定义的问题。”
- “平台不要求一次替换现有 ERP；我们会先确认系统记录源，再从一条可对账链路开始连接。”
- “是否适合需要结合您的组织层级、交易模式和现有系统判断，我们建议先做范围诊断。”

### 2. 能力演示

- “这里可以看到模板发布前的差异和影响范围；演示租户的数据不会被模板升级覆盖。”
- “这笔业务可以从08的报价和订单意向，追到09的权威确认订单、履约批次，再追到12的财务实际成本和现金状态；各环节仍按您现有合同、财税和审批规则配置。”
- “这个连接器展示了幂等和失败重试；实际吞吐、字段和时效要通过您方沙箱联调确认。”

### 3. 试点建议

- “建议选择一个区域、一个代理或一个产品线，限定数据范围和成功指标，先完成可回退试点。”
- “试点验收可包含租户隔离、一次模板升级、一条交易闭环和一条 ERP 对账链路。”
- “试点结果会说明可复制部分、仍需定制部分和规模化前置条件，不把单点成功直接外推到全量。”

### 4. 处理效果诉求

- “我们可以承诺交付约定功能和验收证据，不能在缺少基线及外部条件时保证收入或转化结果。”
- “性能和可用性会基于部署方案、容量测试和第三方依赖给出目标，不使用脱离条件的绝对数字。”
- “海外上线要逐区评估数据、税务、支付和营销规则；平台提供控制点，但不替代专业法律意见。”

## 五、状态、报价与承诺边界

- 演示、报价和合同必须读取程序标识的“已具备、试点、规划”状态；P0/P1/P2不能代替可售状态。
- 必须使用程序归一化后的 `deliveryStatus`；统一蓝图路由默认是 `planned`，既有真实业务路由默认仍只是 `pilot`，都不能仅因页面可见而宣传为 `available`。
- “开通 / 取消 / 隐藏”是目录展示状态，不是交付成熟度；规划应用即使在栏目中开通，也必须继续标注“规划”，销售不得据此承诺已经可用。
- “已具备”必须附当前版本、真实路由、权限、关键流程、监控和回退证据；“试点”必须附白名单、期限、限制和退出方案。
- 报价应拆分标准产品、连接器、实施、迁移、定制、培训和持续支持，不用模糊总价隐藏依赖。
- 合同中的范围、环境、数据量、并发、第三方费用、客户配合事项和验收样本必须明确。
- 路线图能力标注为“规划”或“试点”，除非另有正式交付条款，不作为当前版本承诺。
- 所有案例和指标须经授权并说明口径；不能把个别客户结果描述为普遍保证。
