# 审批中心运营契约

## 业务定位

审批中心是跨业务的审批控制面，不是报价、采购、财务、人事、招聘或 ERP 的替代系统。各业务系统继续保管权威单据；审批中心只固定来源单据的编号、状态和修订号，执行受控审批，并在终审后生成待业务系统确认的交接记录。

支持的首批来源为 `cpq-quote`、`purchase-order`、`finance-document`、`people-contract`、`recruiting-offer` 与 `erp-posting`。来源必须属于同一项目和租户，并处于该业务允许送审的状态。来源修订号发生变化后，旧审批立即失效，必须重新发起。

## 流程设计与版本

流程状态为 `draft → active`。流程作者不能启用自己的流程；启用动作必须由独立治理人完成并附证据。每个启用版本固定对象类型、1至8个顺序步骤、每级唯一审批人、逐级截止时间、总 SLA 和是否允许代理。已经用于审批请求的版本不可静默改写。

新审批请求固定启用版本以及来源快照。请求状态为 `in-review → approved / rejected / returned`。只有当前顺序步骤可以操作，后级不能抢先审批；发起人不能审批自己的请求。每次动作都追加保存决定、理由、证据、渠道、实际操作者、被代理人和来源版本核验结果。

## 移动审批、代理与超时

Web、移动端和 API 只是操作渠道，不改变权限、职责分离或证据要求。移动端不得因为界面简化而降低身份、权限、来源版本和修订冲突校验。

代理必须限定原审批人、代理人、流程或对象范围、开始时间、结束时间、理由和证据。代理不扩张权限，不允许永久授权，也不改变原流程的责任归属；动作同时记录实际代理人与原审批人。

审批时长以请求提交到最终决定的时间计算；超时率以仍在审批且超过 SLA 的请求计算。超时提醒和升级只能追加审计动作，不能自动替代人的批准。

## 业务交接边界

最后一级通过时，审批中心把请求变为 `approved` 并生成 `ready` 交接，但不修改来源业务单据。业务负责人复核来源修订号没有变化后，把交接变为 `acknowledged`。确认只表示业务系统收到有效审批结果，真正的报价发布、采购下单、财务过账、合同生效、Offer发送或 ERP 过账仍由对应业务服务和权限执行。

因此 `final_approval_mutates_domain_record = false` 永远成立；审批中心不得用通用接口绕过业务系统的自身校验。

## 权限、审计与租户隔离

权限分为流程管理、流程启用、请求发起、请求审核、代理管理和交接确认六项。全部记录携带 `agent_path`、`tenant_id`、`client_id`、`project_id` 与 `plan_id`，每个状态动作同时写业务证据和带项目 ID 的平台审计。修订号阻止陈旧页面覆盖新状态。

- 总部端维护统一审批底线、对象适配和审计规则。
- 代理端只在获得项目权限后担任指定审批人或限时代理，不得跨租户查看或代批。
- 客户端对业务来源、流程授权、审批决定和最终业务执行承担责任。

回滚只删除审批控制面拥有的记录和权限，不删除或修改 CPQ、采购、财务、HR、招聘、ERP 的任何来源单据。生产回滚前必须导出审批中的请求、动作证据和未确认交接。

## 上线验收

必须证明：流程不能自批启用；来源项目、状态和修订号有效；请求不能重复在途；发起人不能自审；只能按顺序审批；代理有范围和期限且不扩权；移动端不降级校验；来源改变使旧审批失效；终审不改业务数据；交接需业务确认；租户隔离、权限、修订、证据、审计、迁移回滚、生产构建、双角色 API 和真实页面闭环全部通过。
